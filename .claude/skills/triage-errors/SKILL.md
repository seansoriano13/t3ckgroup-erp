# Triage errors

Turn what broke in the app (Bugsink) into tickets the user has decided on. Agents investigate. The user decides. Nothing is published before the user says yes to that specific ticket.

Where the errors live: the Bugsink site in `BUGSINK_URL` (see `.env.local`). The helper `node .claude/skills/triage-errors/bugsink.mjs` reads it with a read-only token and keeps a local record of past decisions in `.claude/skills/triage-errors/.state/`. Never print or paste the token. Never use the upload token (`BUGSINK_AUTH_TOKEN`) for reading.

## Hard rules

1. **No ticket, spec, comment or label is published until the user approves that item.** Drafts are shown first, in this chat.
2. **Investigation is read-only.** No code edits, no branches, no commits, no migrations, no writes to Bugsink (the token cannot write anyway).
3. **No personal data in anything you write.** Reports are already scrubbed. If a name, email or amount still shows up, leave it out of tickets and tell the user.
4. **Every issue or comment posted starts with** `> *This was generated by AI during error triage.*`
5. **When asking for a decision, follow the user's rule:** say what the thing is, what the problem is, and what happens for each option, in everyday words. Short sentences, no jargon. If you must use a term, explain it once.

## Process

### 1. Scan

```bash
git fetch origin staging --quiet
node .claude/skills/triage-errors/bugsink.mjs issues
```

This lists open errors the user has not decided on yet. An error already decided comes back only if new events arrived after the decision, and it is marked "came back". Use `--all` to see everything.

If the count is 0, say "No new errors." and stop. Do not invent work.

### 2. Investigate (agents, in parallel, read-only)

Start one agent per issue (at most 5 at a time; use `general-purpose`, model `sonnet`). Give each the issue id and this brief:

> Read-only. Do not edit files, create branches or run anything that writes.
> 1. Run `node .claude/skills/triage-errors/bugsink.mjs issue <ID>` and read the stack trace, tags, release and `commitsOnStagingSinceThatBuild`.
> 2. Find the code in this repo that runs there. If `commitsOnStagingSinceThatBuild` is above 0, check `git log` for the files involved: was it already fixed since that build?
> 3. Report back in exactly these fields: **Verdict** (real bug / already fixed / noise / not enough info), **Who is hit** (roles, departments, how many events, first and last seen, which environment), **What happens to them** (one plain sentence), **Likely cause** (plain words), **Where** (module and function names, not line numbers), **Size** (Small or Big, using the rubric in the skill, with the reason), **Fix outline** (3 to 6 lines), **Confidence** (high / medium / low and why), **Same cause as** (other issue ids, if any).
> Noise includes: the smoke-test event, browser-extension errors, errors from a build far behind staging that are already fixed, one-off network drops.

### 3. Group and filter

Merge issues that share a cause into one item. Drop noise from the decision list, but list it at the end as "not worth a ticket" with one line of why, so the user can overrule you.

### 4. Size gate

Mark each item **Small** or **Big**.

**Small** means all of these:
- one layer (just the UI, or just a service, or just one SQL function)
- about 3 files or fewer
- no database migration, no RLS or policy change
- no new product decision (how it should behave is already obvious)
- the bug can be shown and the fix checked in one go

**Big** means any of these:
- needs a database migration or a policy / RLS change
- crosses layers (UI + service + database), or more than about 3 files
- touches money, approvals, costing, IPAS, payroll or leave status flows
- the right behavior is a choice, not a fact ("should it block or warn?")
- one issue hides several different causes
- cannot be reproduced, so the cause is a guess

Small becomes a **ticket**. Big becomes a **spec first**: recommend a short grilling to settle the open choices, then a spec, then tickets cut from it. Use the `grilling`, `to-spec` and `to-tickets` skills for that, with the error evidence as the starting input. The same approval rule applies to the spec and to every ticket cut from it.

### 5. Ask the user, one item at a time

Show items in this order: real bugs by most people hit, then Big items, then "not worth a ticket". For each item write this block, then ask:

```
### <short plain title>   (Bugsink: <ID>)

**What happened:** one or two sentences a non-developer understands.
**Who it hits:** roles/departments, how many times, since when, staging or production.
**Why (best guess):** plain words. Say how sure you are.
**Size:** Small or Big, and the one reason.

**Draft ticket:**   (or "Draft spec outline:" for Big)
  Title: ...
  Body: (full text, as it would be posted)

**Your options:**
- Make the ticket → what it means: an agent can pick it up and fix it; it shows in the issue list.
- Spec first → what it means: we talk through the open choices before any fix; slower, safer.
- Ignore → what it means: nothing is made; it stays in Bugsink and comes back here if it happens again.
- Wait → what it means: we want more events before deciding.
```

Use `AskUserQuestion` for the choice (up to 4 items per call, each with those options and their consequences in the option descriptions). Recommend one option and say why. If the user wants changes to the draft, edit it and show it again. Ask again only for what changed.

### 6. Publish, only what was approved

For each approved **ticket**:

```bash
gh issue create --label bug --label ready-for-agent --title "..." --body-file <file>
node .claude/skills/triage-errors/bugsink.mjs decide <ID> ticket "#<number>"
```

Use `ready-for-human` instead of `ready-for-agent` if it needs a person (a judgment call, outside access, manual testing). Write the body to a temp file in the scratchpad, not inline.

Ticket body (follow [../triage/AGENT-BRIEF.md](../triage/AGENT-BRIEF.md) for durability: describe behavior and module names, not line numbers):

```
> *This was generated by AI during error triage.*

## Problem
What users see or what fails, in plain words.

## Evidence
- Bugsink issue: <ID> (<link>)
- <N> events, first seen <date>, last seen <date>, <staging|production>, build <short sha>
- Hit: <roles / departments>

## Likely cause
...

## Where to look
Module and function names.

## Done when
- [ ] The behavior that failed now works (describe it as a check someone can do)
- [ ] A test covers it (name the seam)
- [ ] Nothing in <named neighbouring behavior> changed

## Out of scope
...

bugsink-issue: <ID>
```

For approved **specs**: grill first (if the user agreed to it), write the spec with `to-spec`, show the full text, publish only after the user approves it, then cut tickets with `to-tickets` and show that breakdown for approval too. Link every ticket to the spec as a native GitHub sub-issue and set native blocked-by links between them. Record with `decide <ID> spec "#<number>"`.

For **ignore** and **wait**, record only: `decide <ID> ignore "<reason>"` or `decide <ID> later "<what we are waiting for>"`.

### 7. Report

Finish with a short summary in everyday words: tickets made (with numbers), specs started, ignored, waiting. Remind the user that Bugsink issues stay open until they resolve or mute them in the Bugsink site (the read token cannot change them).

## Notes

- The ledger is local to this machine. Tickets also carry `bugsink-issue: <ID>` so they can be found with `gh issue list --search "bugsink-issue: <ID>"` if the ledger is lost. Check that before making a duplicate.
- Production is not wired up yet. Today every error is from staging, and each report says so. Say it in the block.
- If the helper says the token is missing, tell the user to create a read-only token in Bugsink (Tokens page, project `t3ckgroup-erp`, issues/events/projects read) and save it as `BUGSINK_READ_TOKEN` in `.env.local`. Do not ask them to paste it in chat.
