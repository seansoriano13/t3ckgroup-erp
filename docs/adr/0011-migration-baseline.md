# Migration Baseline

Related: [issue #87](../..), [0007](0007-timestamped-migration-filenames.md) (filename
convention this baseline follows), [0010](0010-staging-is-a-working-environment.md).

`supabase/migrations/` built 17 tables. Both live databases held 57. `supabase db
reset` on a developer machine produced an application that could not run, and
`migrate-prod.yml` replayed a file set nobody had ever demonstrated was sufficient.

## Baseline source: the decision collapsed

The original plan (see the spec on issue #87) was to generate the baseline from
production specifically, reasoning that a baseline gets marked "already applied" in
both ledgers, so it must describe a state both databases have actually reached — and
the spec's own Phase 0 inspection was written expecting production to hold 46 tables
against staging's 57.

That number was wrong. `supabase/schema/prod.sql` had been snapshotted before a
consolidating migration ran against production and had been stale by 14 tables since;
regenerating it (`pnpm db:snapshot:prod`) showed production and staging both carrying
the same 57 base tables, and both migration ledgers already recording the same three
versions. With the databases schema-identical, "generate from production" and
"generate from staging" stopped being different decisions.

In practice the baseline is built from `supabase/schema/staging.sql`, because that is
the exact file the new pull-request gate (`.github/workflows/migration-gate.yml`)
compares a from-scratch build against. Building from it rather than re-deriving the
same content from a second query keeps the acceptance test meaningful: a build from
the committed baseline should reproduce the committed mirror.

**Known residual gap, deliberately not chased:** production and staging have
snowflaked into a handful of physical differences that predate this work and are not
worth reconciling as part of it — an `identity` column using `GENERATED ALWAYS` on one
database and `GENERATED BY DEFAULT` on the other, one `uuid` column defaulting to
`uuid_generate_v4()` on production where staging uses `gen_random_uuid()`, and one
orphan view (`monthly_performance_summary`) that exists on production but not staging.
None of this is exercised by the application; it is recorded here so a future drift
investigation doesn't waste time rediscovering it.

## Section order departs from the schema mirror

`scripts/db-snapshot.mjs` emits sections in this order: Extensions, Tables,
Constraints, Indexes, RLS enable, Policies, Functions, Triggers, Views. That order is
fine for a mirror that is only ever compared against, never executed — but the
baseline is executed, once, against an empty database, and `CREATE POLICY` resolves
the functions its `USING`/`WITH CHECK` clauses call (`public.get_employee_id()`, used
throughout) at creation time. Policies-before-Functions fails outright against an
empty database with "function ... does not exist".

The baseline reorders to Extensions, Tables, Constraints, Indexes, **Functions**, RLS
enable, Policies, Triggers, Views — Functions moved ahead of both Policies and
Triggers, which also create trigger functions' callers. `scripts/db-snapshot.mjs`
itself is unchanged; only the one-time baseline file reorders the same content.

## Verified by actually building it

The baseline was applied to a throwaway local Postgres (the local Supabase stack this
issue also adds) from empty, and the result compared against
`supabase/schema/staging.sql` via `scripts/db-snapshot.mjs --db-url ... --check
--against`. This is the same path `.github/workflows/migration-gate.yml` now runs on
every pull request touching `supabase/migrations/**`. No custom types, non-default
grants, standalone sequences, materialized views, or triggers on the `auth` schema
were found in this schema, which is why `db-snapshot.mjs` — scoped to `public` and
covering only the object kinds it already handles — needed no new sections to produce
a complete baseline here. That won't necessarily hold for every future schema change;
the gate exists so the next gap is caught in a pull request rather than discovered on
staging.

## Ledger repair, not execution

The baseline is marked "applied" in both ledgers via
`.github/workflows/repair-migration-history.yml` (generalized from a staging-only
utility to take a `project` input) — never executed against either live database,
which already has every object it creates. Like `migrate-prod.yml`, this is a
human-triggered workflow: a person presses the button in the Actions tab, CI runs the
command, nobody runs `supabase migration repair` from a developer machine.
