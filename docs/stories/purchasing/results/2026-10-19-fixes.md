# Fix list from the 2026-10-19 purchasing run

Compiled 2026-10-20 from [2026-10-19-run.md](2026-10-19-run.md) and [2026-10-19-notes.md](2026-10-19-notes.md), after checking each finding against the code and settling the open decisions with Sean.

Order: access and money first, then data integrity, then screens, then docs.

## A. Access and money (do first)

### A1 · Final Acquire list can open SORs that have a matrix (run F1, CM-15)
- Today: the approver sees the row in `/approvals/bid-decisions`, but opening the SOR says "You're not on this SOR". Their matrix tier (`closed_book`) is fine; the SOR read is what blocks them.
- Decision: anyone on the Final Acquire list can open any SOR that has a Costing Matrix. No mention needed, and it doesn't end when the stage moves.
- Done when: the approver opens the matrix straight from the Bid Decisions queue on a fresh SOR, and still can after the stage moves.

### A2 · Evaluation list gets the "participant" view (run F2, CM-09/10/11)
- Today: `costing_tier()` gives the Evaluation list nothing, so a member who isn't Purchasing or Deal Team can never see the matrix or approve.
- Decision: the Evaluation list gets the `participant` tier (the matrix with no money), plus the right to open SORs that have a matrix, the same as A1.
- Done when: ops-head (Evaluation list only) opens the SOR, sees specs and compliance with no money columns, and can approve the Evaluation.

### A3 · Sales must not see Landed Cost (new failure F6, found while checking)
- Today: `costing_can_read_money` allows `closed_book`, `cost` **and `price`**, and both Landed Cost reads use it (`costing_landed_costs`, and the Landed Cost total in `ipas_summaries_for_sor`, in `20261019200000_landed_cost_flows_back.sql`). Sales would see the real cost as soon as an IPAS feeds it. The columns were only empty in the run because nothing had been bought yet.
- Decision: only Closed Book and the cost tier (Purchasing) read Landed Cost. The database refuses Sales, not just the screen.
- How: add a separate check for Landed Cost (closed_book + cost) and use it in those two places. Leave `costing_can_read_money` alone for the Canvass reads.
- Also check: the Canvass Offer prices are read through `costing_can_read_money` too, which lets the price tier see suppliers' quoted unit prices (also cost). See whether `20261020100000_canvass_offer_projection.sql` already handles this; if not, give it the same fix.
- Done when: sales-exec gets no Landed Cost columns or values, and a direct database call returns no rows. Purchaser and approver still see it.
- Glossary updated: CONTEXT.md, "Closed Book".

### A4 · Purchasing can't give "Checked by" (run F5, IPAS-21)
- Today: `ipas_set_header` only limits people outside Purchasing (`20261014120000`, near line 339), so a purchaser can set `checked`.
- Fix: Purchasing may move Computation status only up to LC Odoo Done. Only Finance, or a Super Admin who isn't in Purchasing, gives or takes back Checked by. The button is hidden for Purchasing too.
- Done when: as purchaser, Checked by can't be clicked and a direct call is refused; finance still gives and takes it back.

## B. Data the server must check for itself

### B1 · The server checks Odoo itself (run F4, plus the forged Odoo copy on IPAS create)
- Today: `purchase_request_set_item_status` saves whatever `po_verification` the browser sends, and `ipas_create` saves whatever Odoo copy the browser sends.
- Decision: a server function asks Odoo itself and then saves. The database no longer accepts a "verified" mark or an Odoo copy from the browser.
- Done when: a direct call with a made-up PO and `"VERIFIED"` doesn't save as verified, and a forged copy is never stored.

### B2 · A PO that Odoo doesn't know is refused
- Decision: refuse "not found in Odoo". If Odoo can't be reached, save the PO as "not checked" with a warning. (This assumes buyers create the PO in Odoo before marking the item Ordered.)
- Done when: P9999999 is refused when an item is set to Ordered, the same as on IPAS raise.

### B3 · Fix a wrong PO on an Ordered item
- Decision: Purchasing may correct the PO number while the item is Ordered (not yet Received). It is checked against Odoo again, and the old number stays in the history.

## C. Screens

### C1 · Section numbers count up by one everywhere
- Decision: use 1, 2, 3, 4 … (the IPAS screen's numbering) in every label and message: Settings → Sign-off lists, notices ("IPAS ready to receive"), and the change log. The stored numbers (1, 3, 7) stay internal and never show.

### C2 · "Your move" names the viewer's own step
- Decision: if you can act, it says "Waiting for you: X". If not, it says "Next: X, waiting on <list name>". This fixes both the purchaser and the technical cases.

### C3 · IPAS Remarks can be edited
- Decision: Purchasing can edit Remarks until the IPAS is filed. The SOR list stays fixed (to change it, cancel and raise again). Update IPAS-22 to match.
